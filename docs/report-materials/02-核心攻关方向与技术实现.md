# 核心攻关方向与技术实现

## 一、多源时序数据驱动的设备健康评估与故障早期预警

### 1. 需要解决的工程问题

垃圾焚烧发电设备运行工况变化明显，同一指标在停机、启动、低负荷和高负荷下不能使用同一阈值。项目需要把分散的振动、温度、电流、压力、转速转换为可比较的健康状态，并保留触发证据，避免只有“报警/不报警”的黑盒结果。

### 2. 输入数据

- 设备台账：设备编号、类型、区域、运行状态、工况和负责人。
- 时序指标：振动、温度、电流、压力、转速。
- 工况：停机、启动、低负荷、稳定运行、高负荷稳定运行。
- 规则数据：工况基准、允许范围、关键范围和设备类型权重。

### 3. 核心方法

`packages/shared/src/health.ts` 根据工况取得各指标基准，通过 `calculateIndicatorDeviation` 计算超出允许范围后的归一化偏离，再由 `calculateContributions` 叠加设备类型权重，最后由 `calculateHealthScore` 形成0—100健康度，并结合关键指标越限调用 `determineRiskLevel` 分级。

### 4. 技术流程

工况识别 → 工况基准切换 → 五项指标偏离度 → 设备类型权重 → 指标贡献度 → 综合健康度 → 风险等级 → 预警与趋势证据。

### 5. 当前代码实现

- 健康算法：`packages/shared/src/health.ts`。
- 模拟时序：`packages/shared/src/mock.ts#createMockTelemetry`，使用固定种子生成最近30天和最近24小时细粒度序列。
- 聚合接口：`apps/server/src/services/operations-service.ts#dashboard`。
- 页面：`DashboardPage.tsx`、`EquipmentDetailPage.tsx`、`AlertsPage.tsx`。
- 测试：`packages/shared/src/health.test.ts`。

### 6. 系统输出

设备健康度、风险等级、指标贡献度、24小时/7天/30天趋势、异常指标和预警详情。

### 7. 典型示范场景

1号引风机在高负荷稳定运行下，最近6小时振动由约4.2 mm/s升至6.8 mm/s，温度由约72℃升至86℃，模拟健康度降至68并形成二级预警。

### 8. 可用于报告的创新点

不是对所有工况使用单一阈值，而是把工况基准、设备类型权重和指标贡献度组合为可解释健康评估链路，使预警能够回答“哪个指标、在什么工况下、以何种程度偏离”。

### 9. 当前实现边界

基准、权重、遥测和健康度均为比赛演示规则与模拟数据；未接入DCS/PLC、真实振动频谱或历史故障标签，不能宣称具备生产准确率或剩余寿命预测能力。

### 10. 后续可扩展方向

接入真实时序数据库和边缘采集网关；按设备型号校准基准；引入变点检测、时序预测和故障分类；用维修结果对规则阈值和模型参数进行闭环评估。

## 二、维修历史、故障诊断与备件库存融合的智能运维决策

### 1. 需要解决的工程问题

传统预警往往停留在提示层，未连接检修负责人、处理时限、备件可用性和维修验证，容易形成“报警很多、闭环很少”。项目需要把研判结果转化为可执行工单，并在完成前确认库存和维修记录。

### 2. 输入数据

- 当前设备、预警、异常贡献和趋势证据。
- 结构化知识库：现象、原因、检查步骤、处理方法、安全提醒、关联备件。
- 工单状态、负责人、时限、检查结果和维修结果。
- 备件当前库存、安全库存和实际消耗数量。

### 3. 核心方法

`IntentRouter` 将问题路由到设备、工单、备件或知识查询；`buildRuleBasedDiagnosis` 检索相关知识并生成结构化证据链；`OperationsService` 把预警转为工单，通过显式状态机推进，并在完成前执行库存预检查和幂等控制。

### 4. 技术流程

预警与问题 → 意图识别 → Repository按需查询 → 规则研判 → 推荐检查与备件 → 创建工单 → 状态机推进 → 库存预检查 → 效果验证 → 库存扣减、预警关闭、知识候选。

### 5. 当前代码实现

- 意图路由：`packages/shared/src/intent-router.ts`。
- 规则研判：`packages/shared/src/diagnosis.ts`。
- 工单状态机：`packages/shared/src/workflow.ts`。
- 业务闭环：`apps/server/src/services/operations-service.ts`。
- 工单页面：`apps/web/src/pages/WorkOrdersPage.tsx`。
- 库存页面：`apps/web/src/pages/SparePartsPage.tsx`。
- 知识库页面：`apps/web/src/pages/KnowledgePage.tsx`。

### 6. 系统输出

风险判断、趋势证据、疑似原因、检查项目、建议时限、关联备件、待处理工单、库存可用性、维修记录、验证结果和知识候选案例。

### 7. 典型示范场景

1号引风机预警生成维修工单后，依次接单、开始检修、填写检查与维修记录、选择风机轴承和润滑油、进入待验证，再以健康度92完成验证。系统更新设备状态、关闭关联预警、扣减备件并写入候选案例。

### 8. 可用于报告的创新点

把“诊断建议”与“能否执行”连接起来：推荐备件在工单中被选择，库存不足会阻止完成；只有填写检修结果和验证结果才能闭环，从而形成风险、任务、资源和效果的一致数据链。

### 9. 当前实现边界

规则研判不是大模型推理；知识条目和备件库存默认来自演示数据；未连接企业ERP、EAM或采购审批；自动督办和日报虽有受保护接口，但仍需外部定时器触发。

### 10. 后续可扩展方向

对接ERP库存与采购、人员排班和安全票证；引入工单耗时与故障复发统计；在专家审核后将维修案例转为可检索知识；建立诊断建议采用率和维修效果指标。

## 三、面向电厂、设备和故障部位的多层级可视化与飞书协同闭环

### 1. 需要解决的工程问题

管理者需要全厂风险分布，设备工程师需要单机趋势，检修人员需要具体故障部位与可执行工单。不同角色还需要在日常使用的飞书中接收、查询和操作，而不是反复切换系统。

### 2. 输入数据

全厂设备状态、系统区域、预警、工单、三维语义节点、飞书消息和卡片操作事件。

### 3. 核心方法

Web端用设备拓扑实现全厂层级，用设备详情实现单机层级，用React Three Fiber加载本地GLB并以语义节点映射实现部件层级；服务端用统一业务服务连接网页、飞书多维表格、机器人消息、WebSocket卡片回调和Webhook备用入口。

### 4. 技术流程

全厂拓扑发现风险 → 进入设备详情 → 打开3D模型 → 切换故障场景并定位部件 → 生成工单 → 飞书多维表格写入 → 机器人卡片通知 → 长连接接收查询/接单 → 状态机更新 → 网页刷新状态。

### 5. 当前代码实现

- 全厂拓扑：`apps/web/src/components/dashboard/EquipmentTopology.tsx`。
- 3D页面：`DigitalTwinPage.tsx`、`features/digital-twin/`。
- 模型：`apps/web/public/models/induced-draft-fan-enhanced-v1.glb`，保留原模型回退。
- 飞书Repository：`FeishuBitableRepository`。
- 机器人与卡片：`notification-provider.ts`、`feishu-callback-service.ts`。
- 长连接：`feishu-ws.ts`、`feishu-ws-bridge.ts`。

### 6. 系统输出

全厂设备拓扑、风险节点、设备趋势、三维部件高亮、结构化研判、飞书预警卡片、机器人查询回答和同步工单状态。

### 7. 典型示范场景

在3D工作台选择“轴承温升”，驱动端轴承语义定位节点被高亮，右侧显示82℃、5.2 mm/s、健康度42和规则场景概率89%；用户可从高风险场景创建工单，再在飞书卡片中确认接单。

### 8. 可用于报告的创新点

同一设备从全厂拓扑、单机时序到三维部件逐级穿透，并把三维场景上下文带入工单；飞书消息查询和卡片操作复用同一意图路由与工单状态机，减少展示系统和协同工具之间的逻辑分叉。

### 9. 当前实现边界

增强GLB是轻量级语义数字孪生，不是厂家级机械复原；故障高亮和概率为演示场景；本地长连接适合比赛展示，不代表已建设生产高可用消息集群。

### 10. 后续可扩展方向

接入真实点位与三维节点绑定、巡检照片和视频；增加多厂区与多机组拓扑；把本地长连接迁移到内地常驻服务；完善飞书卡片审批、值班群分发和权限审计。
